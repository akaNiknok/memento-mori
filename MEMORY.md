## Deployment & triggers
- **Everything live is the Worker.** GitHub Flow since 2026-10-03: `npm run release -- patch|minor` on a feature branch bumps, tests, pushes and opens the PR into `main`; it does NOT release. **Merging that PR is what ships:** `release.yml` runs migrations → `wrangler deploy` → tag → GitHub Release. A UI-only change still needs the deploy; a GAS change needs `npm run push` and nothing else (no deployment exists to redeploy).
- **Worker secrets** (Cloudflare only): `APP_PASS`, `SECRET_TOKEN`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_USER_ID`, `GEMINI_API_KEY`, `INGEST_TOKEN`, `IBKR_FLEX_TOKEN`, `IBKR_FLEX_QUERY_ID`. `worker/.dev.vars` (gitignored) holds the same names for `wrangler dev`. **`GAS_URL` is deleted.**
- **GAS script properties:** `WORKER_URL`, `INGEST_TOKEN`, optional `GMAIL_HINTS`/`GMAIL_QUERY` (neither is set — `cfg_` falls back to the `GMAIL_HINTS_`/`GMAIL_QUERY_` constants in `Gmail.gs`), plus the machine-written `GMAIL_LAST_TS` and `BACKUP_FILE_ID` (`BACKUP_SHEET_ID` is dead from v3.2.0 — delete it and the old spreadsheet by hand). Everything else was deleted or moved.
- **Settings that used to be script properties now live in the `meta` table** and are editable on the Admin screen: `monthly_income_php`, `usd_php_fallback`, `fire_real_return`, `owner_email` (+ machine-written `tg_last_ids`, `app_url`). `data_version` and `ledger_first_year` were dead rows; `0006_drop_dead_meta.sql` deleted them (2026-09-25). **The Gemini `intent` is an enum since 2026-09-25** (`log|query|balance|undo|none`): as a plain STRING the model invented `"error"`/`"none"`.
- **Triggers:** two Cloudflare crons in `wrangler.toml` (so they ARE in source): `0 22 * * *` = 06:00 Manila, IBKR prices then the net-worth snapshot; `*/2 * * * *` = the Telegram rescue drain (v2.12.0). `[env.staging.triggers] crons = []` stops staging inheriting them. Apps Script keeps two: `gmail_ingest` every 5 min, and `backup_run` nightly (install with `backup_install()`). **Cloudflare does not retry a failed cron** — `runCron` catches and Telegrams the owner.
- **Backups, three layers:** the nightly Apps Script pull into ONE JSON file on Drive (v3.2.0; it was a spreadsheet, and `setValues` coerced the types so the dump did not reload), the Admin screen's per-table CSV, and D1 Time Travel (7 days, free).
- **Free-tier headroom:** static assets are unmetered; only `/api`, `/login`, `/tg` and the crons burn invocations — a few hundred a day against 100k. D1 usage is thousands of read rows and dozens of writes against 5M/100k. The 10ms CPU cap excludes I/O wait, and the dashboard's aggregation is pushed into SQL for exactly that reason.

- **IBKR Flex token expires within a year of creation** — the one recurring maintenance task; HANDBOOK.md has the dated-task row. Expiry symptom: the price cron Telegrams a failure and share values go stale.

- 2026-09-16 (`getDebts`): **a receivable's balance is itemised by ALLOCATION, not by a stored "paid" flag — and the ordering was chosen against the real ledger, not from taste.** The ask was to see the individual debts behind a receivable account with the least possible friction at logging time. **A `debts` table with a paid status was rejected twice over:** it is a second source of truth that drifts the first time a transaction is edited, and it puts a mark-paid step on every settlement — the exact friction the request was trying to avoid. So nothing is stored: the account's legs are folded in date order, a leg that pushes |balance| UP opens an item and a leg that pulls it toward zero settles the open ones. **The sum of the open items IS the balance**, which is the invariant `test-api.js` asserts against the independent `deltas()` path, and it is why this can never drift. **FIFO, and NOT LIFO — measured, on the real data before it was written.** One receivable carries a gadget bought on the owner's card and repaid in 12 equal instalments, wrapped in a year of small round trips. FIFO landed within 0.5% of the instalment arithmetic and smallest-first within 3%, but **LIFO was out by 28%**: it holds the charges made days BEFORE the big one open for ever and pays the big one down that much too fast. Smallest-first fails the other way — it is the debt-snowball rule, so every payment goes to the small items and the big debt never visibly moves, which is the one thing the screen exists to show. **The ordering only ever decides LABELS; the total is right under all three.** **`cancelRoundTrips` is the part that was NOT obvious and is load-bearing.** A plain date-ordered fold mislabelled most of the real ledger, for two reasons that both had to be fixed in a pre-pass rather than inside the fold: ① a round trip is as often recorded settlement-FIRST (the repayment lands the same day as the charge, or the day before it clears), and the fold then spends that repayment on some older debt and leaves the charge open for ever; ② **ONE transfer routinely repays SEVERAL debts** — this was the owner's own stated worry — and one-leg-to-one-leg matching cannot see it. Matching a leg against a *run* of nearby opposite legs summing exactly to it fixes both, in either direction, and cannot move the balance because it removes a set that sums to zero. On the real data it cancelled exactly the five genuine round trips and nothing else. **`ROUNDTRIP_DAYS` is 14** — the real pairs settle in 0-9 days; the exact-sum requirement, not the window, is what keeps it honest. **Known and accepted:** where an old unsettled pile predates the big debt, FIFO spends payments labelled "for <the big thing>" on that older pile, so the big item's remaining figure is a convention, not a reading of the descriptions. Matching on the description keyword would fix it and was NOT built — it is fuzzy text matching, and the totals are right either way. Revisit only if the labels actually mislead.
- 2026-09-13: **`delete_branch_on_merge` is ON, on purpose — and the back-merge is what makes that safe.** A release PR is `develop` -> `main`, so GitHub deletes `develop` at the merge; `develop` is deliberately unprotected and gets no exemption. Nothing breaks, because the `backmerge` job in `release.yml` opens with `git push origin "$GITHUB_SHA":refs/heads/develop`, and a push to a branch that is absent CREATES it — at `main`, which is exactly where the fast-forward would have put it. So `develop` is gone for the seconds between the merge and that push, then it is back. Supersedes the earlier note that said to keep the setting off.
- 2026-09-13 (v2.14.2): **an HTTP error with no `<ErrorCode>` is not IBKR — the poll stops at once instead of spending the patience budget.** The 06:00 job died with `Flex statement not ready after 6 tries. Last reply: 403 error code: 1000`. **1000 is not an IBKR Flex code**, and the give-away is the message shape: `flexWhy` prints `<ErrorCode> <ErrorMessage>` when IBKR answers and falls back to the stripped body when it does not, so a bare `error code: 1000` means the reply carried NO error code. `error code: NNNN` in plain text is an EDGE error page, not a Flex reply. Probing the live service the same morning confirmed the other half: **the Flex service answers HTTP 200 with XML even when it refuses** (a dummy token gets 200 + 1015 on both ndcdyn and gdcdyn, and our exact `User-Agent` is accepted), and IBKR sits behind Akamai, not Cloudflare. **So any non-200 means the request never reached the Flex service** — no token, query, reference code or UA is implicated, and there is nothing in Client Portal to repair. Root cause of the FAILURE was outside us and transient; root cause of the job DYING is ours: `flexPoll` treated 'no `<ErrorCode>`' as 'still generating', so six polls of ~32s all went to the same shut door and the one recovery lever the job owns — a fresh `SendRequest`, which re-resolves the host and goes via ndcdyn first — never fired, because it hangs off `got.stale` and a 403 sets no code. Fix: `res.status >= 400 && !code` returns `{blocked}`, which stops that poll and takes the same single-retry path a dead reference code takes; the failure message now says **blocked before IBKR answered** rather than **statement not ready**, because the two need different repairs and the old wording sent the owner at the annual token renewal. - 2026-09-04 (v2.11.2 — the Gmail courier lost three transactions): **a post that THREW no longer moves the watermark past its message.** Symptom the owner saw: two MariBank alerts from 2026-09-03 (DQ Cherry ₱56.43, MercuryDrug ₱66.75) and one from 2026-09-04 (a ₱1000 BPI BanKo → MariBank transfer) were still in the inbox and had no rows, while alerts an hour either side of them landed normally. **Proof of the mechanism, not a guess:** `email_quotes` had no row for any of the three, and `ingestEmail` writes the quote BEFORE `logItems` — so the parse never returned, i.e. the POST threw. The old `gmail_ingest` did `newest = max(newest, ts)` before the try and wrote it unconditionally, so one transient Gemini failure retired the message for ever; the mail stayed in the inbox with nothing looking at it again. **The comment that justified this was wrong:** it feared an unparseable email replaying every 5 minutes, but a genuine non-transaction comes back HTTP 200 `logged 0 of 0`, which is a SUCCESS on this path — only a real fault (Gemini 429/5xx/timeout, Worker down, bad token) throws. **The fix is 4 lines:** `hold = min(hold, ts - 1)` in the catch, and the watermark is `min(newest, hold)` — so the mark stops at the OLDEST failure in a run even when a later message succeeded in the same run. `GMAIL_RETRY_MS_` (3h ≈ 36 tries) bounds it, because a permanently poisonous email would otherwise spend a Gemini call every 5 minutes against a free tier of ~250 a day.
