# CLAUDE.md
Guidance for Claude Code (and humans) working in this repo. **Keep this file and MEMORY.md token-efficient: dense, minimal blank lines, no filler; lines may exceed 80 chars. Apply the same when editing them.**

## Session protocol (read first)
- **Open work lives only on GitHub — one place for each kind:** ① **Unfinished work** → commit, push, open a **draft PR** whose body says what is left and how to resume. ② **Steps only the owner can do** (a migration, a secret, a smoke test, a later check, a decision) → an issue labelled `owner`: exact commands, a checkbox list, then close it when done. Steps that only matter after a PR merges go there too, linked from the PR — a PR body dies with the merge. ③ **A PR waiting to merge needs no note anywhere** — it is its own to-do. ④ **Backlog ideas** → an issue labelled `enhancement` or `bug`. MEMORY.md holds decisions and facts, never to-dos. The repo is public: name a secret, never its value.
- **Load the skill before you edit the area:** `spa-frontend` for anything in `worker/public/`, `worker-backend` for `worker/worker.js`, `worker/src/*`, the migrations or the SQL, `apps-script` for the `.gs` files. They hold the constraints that used to live in this file; do not re-derive them from the code. **Anything the user sees also follows `DESIGN.md`** (tokens, type, layout, components, tooltips, motion); a new colour or component is added there in the same commit.
- The big files are `worker/public/app.js`, `worker/src/api.js` and MEMORY.md — read targeted sections, not the whole file, when you know what you need. `MEMORY-ARCHIVE.md` is retired history; leave it closed unless the question is why something used to work that way.

## Communication style (how to talk to the owner)
Owner holds a **BS in Management Information Systems**. Bridge IT and strategy: frame a technical trade-off as system integration, scalability, data flow or value. Do not over-explain foundational tech and do not walk through low-level syntax.
**Write in Simplified Technical English (ASD-STE100 spirit, not the strict standard) — chat prose, commit messages, docs. README.md and HANDBOOK.md keep the strict version (see their row).**
1. Use active voice. Write "The system sends the file", not "The file is sent by the system". 2. Put one idea in each sentence; split a sentence that has two. 3. Keep sentences short — no word count, but cut every word that adds nothing. 4. Use a maximum of three words in a noun cluster: "the log of failed jobs", not "the failed job log record". 5. Use one term for one thing — if it is a "data pipeline", it is never later a "data flow" or an "ingestion path". 6. Use one meaning for each word; do not use "run" for both execute and manage. 7. Start an instruction with the verb: "Open the panel", not "The panel must be opened". 8. Expand an acronym at first use only. 9. Use lists for steps and comparisons; use prose for reasoning.

## Project overview
**Memento Mori** is a **personal finance tracker**. Since **v2.0.0 (2026-08-23) the backend is a Cloudflare Worker over Cloudflare D1** — one Worker serves the PWA, the JSON API, the Telegram bot and two cron jobs. Google Sheets is gone as the source of truth (frozen archive; the v1 backend is `git show v1.9.2:Transactions.gs` etc.).
- **Three ways in, one set of handlers:** the **PWA** (`worker/public/`), the **Telegram bot** (`worker/src/telegram.js`), and **Gmail ingest** (Apps Script courier → `?action=ingestEmail`). All route through `worker/src/api.js`. A fourth door is **read-only**: `POST /mcp` (`worker/src/mcp.js`, own token `AI_READ_TOKEN`, or an OAuth token from `worker/src/oauth.js` for claude.ai) lets an AI client read the ledger.
- **What is left in Apps Script:** `Gmail.gs` (mail courier, 5-min trigger) and `Backup.gs` (nightly JSON dump onto Drive). **No Web App deployment, no `doGet`/`doPost`, no `deploymentId`, no `GAS_URL` secret.** `GmailApp` is the only reason GAS survives at all — free OAuth to the owner's mailbox with no off-platform equivalent.
- **Locale:** amounts in **PHP**; timezone `Asia/Manila`.
- **History:** v1 (GAS + Sheets, v1.0.0→v1.9.2) is the design record — `git show v1.9.2:CLAUDE.md` for the sheet-era lore, `git show v1.3.4:OVERHAUL_PLAN.md` for the original overhaul. The v2 cutover is done and its one-shot kit is deleted — `git show v2.3.1:D1_MIGRATION.md` for the execution plan, and the same for `Export.gs`, `migrate/import.js`, `migrate/verify.js`.

## Git workflow (GitHub Flow, since 2026-10-03)
- **`main` = live, and the only long-lived branch.** Every change is a short branch off `main` and one PR back into it. `develop`, the back-merge job and the separate hotfix path are gone (`git show v3.6.0:.github/workflows/release.yml` for the Gitflow era). Read history with `git log --first-parent main`: one merge commit per PR.
- **Branches:** `feature/<name>` or `fix/<name>`. **Create it with `git switch -c feature/<name> --no-track origin/main`.** `git checkout -b <name> origin/main` sets the UPSTREAM to `origin/main`, so a bare `git push` aims at `main` — the push hook only sees the word `main` in the command, and `enforce_admins` is off, so the owner's push would land (this happened with `develop` on 2026-08-30). With `--no-track` a bare push refuses until you name a branch.
- **Release: a merge into `main` whose version is not yet tagged is the ONLY way code reaches live.** `.github/workflows/release.yml` runs `npm test`, D1 migrations, `wrangler deploy`, tag `v<package.json version>`, GitHub Release, in that order (new code must never meet an old schema). A merge with an already-tagged version does nothing — docs, tests and `.gs` PRs merge without a deploy. **CI refuses a PR that changes `worker/` without a bump**, so `main` never holds code that is not live. The Cloudflare token lives in GitHub repo secrets; nothing needs a local credential.
- **Shipping a change:** on the branch, `npm run release -- patch|minor`. It bumps (`stamp-version.js` writes `index.html`'s `brand-ver` span and stages it — never hand-edit it), commits, runs the tests, pushes and opens the PR into `main`. It **does not release**; merging the PR ships. Without an argument it skips the bump (a re-run on a bumped branch). A no-deploy change needs no script: `gh pr create --base main`. A hotfix is the same flow with `patch`.
- **Tags/Releases invariant:** every tag is `vX.Y.Z`, on `main`, created only by the Release workflow, with a matching GitHub Release. Never hand-create tags or Releases. **The release is unattended:** the `production` GitHub environment has NO protection rules, so the merged PR is the only approval.
- **A PR into `main` that touches `worker/` deploys to staging; `main` deploys to live.** `staging.yml` runs on each push to such a PR; one staging Worker, so the last PR pushed wins. `[env.staging]` in `wrangler.toml` → `memento-mori-staging`, its own D1, **no cron, no bot, no Gmail courier**, one secret (`APP_PASS`). Wrangler inherits most keys into a named environment but **not the bindings** — and `triggers` IS inherited, so the empty `crons = []` override is what stops staging running the 06:00 IBKR job against its own database. `test.js` guards both traps: every `[[d1_databases]]` needs an `[[env.staging.d1_databases]]` copy whose `database_id` DIFFERS, and the crons override must be present. Staging normally holds `seed.sql` data only. **A copy of the real ledger is allowed when the owner asks for one** (2026-09-16, to check a screen against real figures) — with the cost understood: `memento-mori-staging.<subdomain>.workers.dev` is public and holds ONE secret (`APP_PASS`), so the real ledger there is guarded by a passphrase and nothing else, and a copy cannot be un-exposed once made. **Reseed with `npm run seed:staging` as soon as the check is done** — the copy is for a sitting, not a standing state. **An agent cannot make the copy**: exporting the live D1 is blocked as data exfiltration, and routing around that by loading a local `dev:pull` dump instead is the same act by another door. The owner runs the three commands (export → wipe → load); a session may prepare them.
- **`main` is protected (2026-08-30):** PR only, and the `test` check must be green. `enforce_admins` is off, so the owner keeps an escape hatch. GitHub deletes a branch on merge; `git config fetch.prune true` keeps the local remote list honest.
- **What an agent may merge:** a green PR with **no version bump** (nothing deploys) — wait with `gh pr checks --watch`, never merge red. **A bumped PR waits for the owner's word in that session**, because its merge deploys to live. Never push to `main`; the push hook blocks it.
- **Undoing a release:** `npx wrangler rollback` puts the last good Worker version back in seconds. **Migrations do not roll back** — so an old Worker must still run against the new schema. Never ship a destructive migration (a dropped or renamed column) in the same release as the code that needs it; add in one release, remove in the next. HANDBOOK.md has the procedure.
- **Worktrees** (`git worktree add .claude/worktrees/<name> -b <branch>`) let a second branch run beside unfinished work with nothing stashed. **Run `npm run bootstrap` inside a new one before anything else** — `node_modules`, `worker/.dev.vars` and the dev port are all gitignored, so a worktree inherits none of them. Remove one when its branch merges. `.claude/worktrees/` is gitignored.

## Conventions & gotchas
- **Never commit credentials** or any URL/id that acts as one. `.clasp.json` (`scriptId` only) is safe; `worker/.dev.vars` and `.clasprc.json` are gitignored.
- **Every "today" goes through `manilaToday()`.** A defaulted transaction date and the BIR quarter window are the two places a UTC slip silently corrupts data.
- **Month keys are `yyyy-MMM` with exactly that capitalisation, everywhere.**
- **The Growth segment rides the FUNDING transfer** (Wise→IBKR, category `Investment: Growth`, budget Monthly $200 = "did I park this month's $200"); broker buy legs (IBKR→ticker/IB01) and EF parking are `Transfer: Internal` — tagging both legs double-counts budget actuals. **There is deliberately NO Stability category or budget row** (removed 2026-08-26): EF accrues as unspent residue, which a monthly meter can't track — the Emergency-runway card is the only EF measure. The convention lives in the category DESCRIPTIONS (which the Gemini prompt inlines, so the bot follows it); `getInvestments`' pulse derives buys from account subtypes, not categories, so it needs no discipline — and from the GROWTH tickers only (`isPulseAcct`): an EF park (IB01, subtype `EF`) is a holding and runway cash, never a pulse buy (v2.9.1). Runway = the `isInvestedNetWorth` liquid side minus receivables minus credit.
- **A UI-only change is not live until the Worker redeploys** — `worker/public/` ships with the Worker, so it rides the same release as backend code; there is no separate asset upload. Nobody runs `wrangler deploy` by hand any more, the merge into `main` does it. A GAS change is the exception: `npm run push` from the owner's machine and nothing else (no deployment exists, and clasp needs interactive OAuth, so no session can do it).
- **Accounting conventions (v2.5.0/v2.6.0, from the accounting-soundness review).** ① **A refund is a NEGATIVE-amount Expense row in the ORIGINAL category** — never `Income: Other`, which overstated both sides. ② **Reports are sign-aware**: budgets, dashboard spend/flow and the runway's average spend sum `amount_php_u` signed, never `ABS()`, so a refund nets its category down; Telegram's `querySummary` keeps `ABS` on purpose ("how much moved"). ③ **A cross-currency transfer that lands in PHP stamps the IMPLIED rate** (`ToAmount/Amount`), not the live rate — the live rate hid the conversion spread; an explicit `ExchangeRate` still wins. ④ **The month close is yesterday's month**: the cron stamps `monthOf(manilaYesterday())`, so the run on the 1st closes the previous month with its last day in it. ⑤ **A negative receivable is a liability** — it reports under liabilities and shortens the emergency runway; a positive one is neither (money lent is not reachable). ⑥ **`liabilities` is NEGATIVE everywhere** — API, `nw_snapshots`, `netWorthTotals`; only the SPA hero absolutes it. ⑦ **`amount_u` is never zero** — rejected on every write path AND a DB CHECK since `0003_tx_checks.sql` — but it may be negative. ⑧ **The `transactions` invariants live in the SCHEMA (v2.6.0):** `amount_u != 0`, `(to_account_id IS NULL) = (to_amount_u IS NULL)`, `fx_rate IS NULL OR fx_rate > 0`, and a real month/day in `date`. A `wrangler d1 execute` escape hatch now fails on a bad shape too — that is the point. The migration recreates the table (SQLite cannot add a CHECK in place); it **copies the rows FIRST**, so a row that breaks a CHECK aborts it with the live schema untouched. ⑨ **A SELL is a transfer OUT of the ticker account** (Amount = share quantity, ToAmount = the money); on a share-priced source `amount_u` is a QUANTITY, so **every peso aggregate that can see a Transfer carries `NOT_SHARES_SRC`** (db.js) — budgets today; the bot's `querySummary` does the same check in JS. Dashboard spend/flow are Income/Expense-only and need none. ⑩ **Cost basis is average-cost** (v2.7.0): a sale removes cost in proportion to the shares leaving, so the average entry price never moves on a sale. `costPhp` is historical (the rate stamped on each buy leg), `investedNative` is the house-money figure (cash in minus proceeds out) and goes negative; a position funded from two currencies reports no native figure at all.
- **Local dev needs no passphrase and no real data (2026-08-30).** `/api` skips the auth check when the request host is `localhost`/`127.0.0.1` (`isLocalDev` in `worker.js`) — Cloudflare cannot route a production request to that host, so it is inert once deployed. `npm run dev:seed` fills the LOCAL D1 from `worker/seed.sql`, invented data modelled on the real database's shape; it REPLACES whatever is there, a `dev:pull` included. So an agent can now open the SPA and read every screen. `npm run dev:pull` is still the real ledger and still denied to agents.
- **A new pure helper gets a test in `test.js`;** anything touching SQL or a handler gets one in `test-api.js`; a new invariant whose failure is silent gets a contract guard. (The push hook already runs `npm test` for you.)
- Keep **MEMORY.md** current: decisions, trigger setup, secret locations.
- **Keep HANDBOOK.md current whenever a change touches the human's world** — a new/renamed secret or `meta` key, a new trigger or schedule, a new hosted service, a changed deploy/migration step, a new manual setup, a new failure mode worth a troubleshooting row, or a stack change. Pure code/refactor/UI-behaviour changes need nothing. A change a visitor would notice (a new screen, a stack change) also updates README.md. Same commit as the change. **Public repo: names of secrets, never values or URLs.**
